# Behavioral implementation

Derive an observable expectation from accepted intent or independent worked examples. Select the smallest existing public seam that exposes the real behavior; state what it catches and misses when consequential. Confirm with the user only when the seam changes a user-owned choice, not for routine test placement.

For testable new behavior or reproducible defects: choose one meaningful scenario, run a failing check on the missing behavior (check the failure reason), make the smallest complete change, run green, and repeat. Do not bulk-write imagined tests, assert internal call shapes, or compute the oracle using the production algorithm. Existing passing coverage is not a RED; if a useful RED cannot be run, state the limit and use the closest actual observation. Refactor when justified, not compulsorily each cycle. Inspect real callers and rejection paths. Characterize intended behavior before structural refactors; for rework define scenarios independently of the invalid premise and update obsolete expectations with explicit rationale, never to hide failure.

Prefer deterministic fixtures, isolated state and pinned seeds; use property-based tests only when a meaningful independent invariant and non-vacuous inputs justify them. Retain counterexamples. Reuse installed tests and gates; focused checks while iterating, broaden for affected interfaces, build/config changes, trust boundaries, integrated or explicitly requested coverage. Reuse evidence only while relevant inputs and revision remain valid.

As a meaningful slice closes, patch affected [wiki claims](wiki.md) and preserve an authorized [checkpoint](git.md) before accumulating unrelated risk. For tiny understood changes do a focused check; for uncertain algorithms or emergent/visual results use an actual [experiment](experiment.md) instead of fake test-first ritual. Check integrated acceptance with [assurance](assurance.md).
